# Internationalization (i18n)

Agri-SDSS serves user-facing error messages in **French (default) and English**. Backend messages
are translated with [gettext](https://docs.python.org/3/library/gettext.html) via the shared
`agri_i18n` package — never by hand-maintained dictionaries.

## For API consumers

**The platform default is French.** A request that sends no language preference receives French.

### Getting English

Send an `Accept-Language` header, or add a `lang` query parameter:

```bash
# Header — works on every service
curl -H "Accept-Language: en" .../vector-api/som-field-match

# Query parameter — matches pygeoapi's own `lang` parameter
curl '.../processes/msc-observations?f=json&lang=en'
```

`lang` takes precedence over `Accept-Language` when both are present. An unsupported value (`de`,
`es`, …) is ignored, falling back to the header and then to French.

### What changes, and what does not

Only the human-readable message text changes. HTTP status codes, response structure and field names
are identical in both languages:

```text
POST /vector-api/som-field-match   {}

no Accept-Language   →  HTTP 422  {"detail":"Le champ « geometry » est requis"}
Accept-Language: fr  →  HTTP 422  {"detail":"Le champ « geometry » est requis"}
Accept-Language: en  →  HTTP 422  {"detail":"'geometry' field is required"}
```

> **If your client string-matches on error text, pin the language explicitly.** Scripts written
> before this change assumed English; they now receive French unless they send `Accept-Language: en`.

### Scope

| Translated | Always English |
| --- | --- |
| Input-validation errors a caller can act on | Upstream/infrastructure failures (OPeNDAP, Copernicus, database) |
| Missing or malformed request fields | Server-misconfiguration messages |
| Not-found errors for user-supplied IDs | Server logs — kept English so they stay greppable |

`stac-api` and `raster-api` emit no hand-written messages; they relay their upstream libraries
verbatim, in English. `gis-pipeline` is an operator CLI and stays English.

Process titles and descriptions in `process-api` are **not** gettext-managed. They use pygeoapi's
native `{"en": …, "fr": …}` language structs in `process-api/processes/*_metadata.py`, resolved by
`pygeoapi.l10n.translate()`. Add a language there by adding a key to those dicts.

## For contributors

### Writing a translatable message

```python
from agri_i18n import _

raise HTTPException(status_code=422, detail=_("'geometry' field is required"))
```

Interpolate **after** the lookup, with named placeholders:

```python
logger.warning("Invalid geometry: %s", exc)          # log stays English
raise HTTPException(
    status_code=422,
    detail=_("Invalid geometry: {error}").format(error=exc),
)
```

> **Never put an f-string inside `_()`.** `pybabel` extracts msgids statically, so
> `_(f"Invalid geometry: {exc}")` produces no catalog entry and silently never translates. Named
> placeholders (not positional) let translators reorder them.

Messages are authored in English — the English source string *is* the msgid. Only non-English
catalogs are shipped; an English request falls through to the untranslated msgid.

### Workflow

```bash
make i18n-extract   # rescan sources for _() calls -> agri_i18n/messages.pot (local only)
make i18n-update    # merge new msgids into agri_i18n/locales/<lang>/LC_MESSAGES/messages.po
make i18n-compile   # compile .po -> .mo locally (images compile their own at build time)
make i18n-check     # the CI gate, see below
make test-i18n      # run the agri_i18n test suite
```

`make i18n-check` runs in CI on every PR and fails on:

- a `_()` call whose argument is not a literal string (an f-string never translates)
- a msgid in the source that no catalog carries, or a stale msgid no longer in the source
- an empty or `#, fuzzy` `msgstr` in any catalog

It compares msgid *sets* between the source and each committed `.po`, not file bytes, so different
Babel versions do not cause false failures.

`messages.pot` is a build intermediate for `pybabel update` and is **not committed** (`.gitignore`
ignores `*.pot`). The `.po` catalogs are the versioned source of truth; the check regenerates the
template itself rather than reading one from disk.

After `make i18n-update`, fill in every empty `msgstr` and clear any `#, fuzzy` marker. Both are
build failures.

`.po` files are committed; `.mo` files are gitignored and compiled in a dedicated `i18n` Docker
build stage, so Babel never reaches a runtime image.

### Adding a language

1. `docker compose run --rm --no-deps -T -v "$PWD:/repo" -w /repo process-api \`
   `pybabel init -i agri_i18n/messages.pot -d agri_i18n/locales -l <code> -D messages`
2. Add the code to `SUPPORTED` in `agri_i18n/__init__.py`.
3. Add the matching locale to `server.languages` in `process-api/config/pygeoapi-config.yaml`, and
   a key to each `PROCESS_METADATA` dict in `process-api/processes/*_metadata.py`.
4. Add it to `ACCEPT_LANGUAGE` in `frontend/home/html/js/utils.js` and the `_ACCEPT_LANGUAGE` map in
   `frontend/home/html/js/chatbot-bridge.js`.

### How the locale is resolved

| Service | Bound by |
| --- | --- |
| `vector-api` | `LocaleASGIMiddleware` on the FastAPI app |
| `process-api` | `LocaleWSGIMiddleware` wrapping pygeoapi's Flask app (`processes/wsgi.py`) |
| `chatbot` | `set_locale(req.language)` from the request body, plus the ASGI middleware for other routes |

The active locale lives in a `contextvars.ContextVar`, so concurrent requests never share it.
`gettext.install()` and a process-global `_` must not be used — they are process-wide and would leak
one request's language into another.

The browser sends the header automatically: `apiFetch()` in `frontend/home/html/js/utils.js` attaches
`Accept-Language` from the active UI language to every same-origin API call.
